# 00 · The hackathon, in our words

> **NOW (results).** Reference for what we're scored on.

A summary of the Real-World Agents Hackathon rules (10 October 2026). The organisers' PDF is not in this repo. Check it for anything binding.

## The brief

Build an agent that works in messy operations: calls, emails, documents, CRM records, tickets. It has to take real actions with tools, handle ambiguity and failures, and know when to stop and involve a person. There are four tracks: insurance claims, property management, banking, and delivery & logistics. Casework is built so one codebase serves any of them (see 03-architecture.md).

## The Reality Test (the core of the score)

- Unseen cases are released 30 minutes before the build deadline. At that point source code and the demo video freeze.
- The cases may contain conflicting information, failed actions, missing context, noise, and situations that need escalation.
- There isn't time to handle them by hand. **The system must run the whole batch unattended** (`pnpm reality`).
- Grading looks at outcomes, acceptable alternatives, positive behaviours, red flags, prohibited actions and critical failures. Escalating or doing nothing can be the right answer.

## Scoring

| Part | Weight | What it rewards |
|---|---|---|
| Correct outcomes + coverage | 38.5 pts | Right resolution, across as many cases as possible |
| Judgement & safety | 14 pts | Ambiguity, conflicts, missing context, knowing when to escalate |
| Engineering quality | 10.5 pts | Architecture, robustness, reproducibility, autonomy |
| Real-world applicability | 7 pts | Could it run in a real operation? |
| Demo video + presentation | 30 pts | Working product, clarity, product insight |

There are also separate awards for exception handling, voice, engineering, and people's choice. An elaborate UI earns no points on its own; the UI exists to make the agent's judgement visible.

## What the repo must contain

1. Working source code with prerequisites, install, config, run steps, env vars and external services documented.
2. `README.md` covering: what we built, the problem, the architecture, how to run it, models/APIs/services, assumptions, limitations, and what's next.
3. `ANSWERS/<n>/ANSWER.md` and `REASONING.md` for each Reality Test case. These must be **generated by the system and never hand-edited**. They show what it received, the actions it took, its outputs, what it escalated, what failed, and the final result. Include logs or traces.
4. A demo video of up to 60 seconds, committed to the repo (Git LFS is fine). A link alone doesn't count.
5. Links to a LinkedIn post and an X post (put them in `SUBMISSION.md`).
6. An Apache 2.0 `LICENSE`.
7. No secrets committed.

## Hard rules

- Don't fabricate results or replace failed outputs.
- Don't put text aimed at the judging model anywhere (prompt injection). Judges test for this.
- After the code freeze, only the video, social links and submission metadata may change.
