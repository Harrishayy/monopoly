    Not using, on purpose

    Saves debate later
    • A separate API server. Next.js route handlers serve REST and SSE. The agent lives in packages/core, so the Reality Test CLI runs it without Next.
    • Redux or a big state library. Server state lives in TanStack Query. The rest is three values (direction, track, autonomy) in Zustand.
    • A charting library. The only charts are the Reality Test grid and tool-health sparklines, which are small enough to draw with CSS or SVG.
    • An agent framework. The loop is about 150 lines on the Anthropic SDK. Owning it makes retries, the policy guard and event emission explicit, which is what engineering-quality judging looks at.
    • A vector database. Each case brings its own sources. Retrieval over a handful of documents fits in context with prompt caching.

    Track packs

    The only place a track is named

    A pack supplies vocabulary, a data loader, tools, policy and a prompt. The UI reads its labels from pack.vocabulary, so a property manager sees "Job" and an insurer sees "Claim" from the same component. To add a track, copy a pack folder and register it. Nothing else changes.

    Data contracts

    Written in zod inside packages/core/src/schema. The API validates with them, the web app parses the SSE stream with them, and Claude's tool input schemas are generated from them. Change a contract in one pull request that updates every user of it.

    // schema/case.ts
export const SourceKind = z.enum(['call','email','doc','crm','ticket','sms','note']);
export const CaseStatus = z.enum(['new','running','resolved','escalated','needs_info','failed','blocked']);

export const Source = z.object({
  id: z.string(),                 // stable, cited by facts
  kind: SourceKind,
  title: z.string(),
  receivedAt: z.iso.datetime(),
  body: z.string(),               // transcript, email text, OCR text
  meta: z.record(z.string(), z.unknown()).default({}),
});

export const Case = z.object({
  ref: z.string(),                // "PM-7731"
  track: TrackId,
  title: z.string(),
  customer: z.object({ id: z.string().optional(), name: z.string() }),
  status: CaseStatus,
  slaDueAt: z.iso.datetime().optional(),
  sources: z.array(Source),
});

export const Money = z.object({   // always minor units
  amount: z.number().int(), currency: z.literal('GBP'),
});
    // schema/events.ts — append-only, one row per event
const base = { runId: z.string(), seq: z.number().int(), at: z.iso.datetime() };

export const RunEvent = z.discriminatedUnion('type', [
  z.object({ ...base, type: z.literal('run.started'), caseRef: z.string(), autonomy: Autonomy }),
  z.object({ ...base, type: z.literal('step.read'), sourceIds: z.array(z.string()), summary: z.string() }),
  z.object({ ...base, type: z.literal('tool.called'), callId: z.string(), tool: z.string(), args: z.unknown() }),
  z.object({ ...base, type: z.literal('tool.succeeded'), callId: z.string(), result: z.unknown(), ms: z.number() }),
  z.object({ ...base, type: z.literal('tool.failed'), callId: z.string(), error: z.string(),
             attempt: z.number(), willRetry: z.boolean() }),
  z.object({ ...base, type: z.literal('action.blocked'), action: z.string(), ruleId: z.string(), why: z.string() }),
  z.object({ ...base, type: z.literal('decision.made'), label: z.string(), rationale: z.string(),
             confidence: z.number().min(0).max(1), citations: z.array(z.string()) }),
  z.object({ ...base, type: z.literal('escalation.created'), handover: Handover }),
  z.object({ ...base, type: z.literal('run.completed'), outcome: Outcome, summary: z.string(), usage: Usage }),
]);
    // schema/handover.ts — what a human needs to decide
export const Outcome = z.enum(['resolved','escalated','needs_info','failed','declined']);

export const Handover = z.object({
  reason: z.string(),                             // one sentence, plain English
  facts: z.array(z.object({ text: z.string(), sourceId: z.string() })).min(1),
  tried: z.array(z.object({ text: z.string(), ok: z.boolean() })),
  options: z.array(z.object({
    id: z.string(), label: z.string(),
    effect: z.enum(['reversible','irreversible','pauses']),
    recommended: z.boolean().default(false),
  })).min(1),
  refused: z.array(z.object({ action: z.string(), ruleId: z.string() })),
  confidence: z.number().min(0).max(1),
  queue: z.string(),                              // "Fraud · Priority"
});

    Import rules

    Enforced by eslint-plugin-boundaries
    • ui/ imports only tokens and other ui/.
    • domain/ imports ui/, lib/ and core types.
    • features/ compose domain and ui. Features never import each other.
    • Client components import core types, schemas and @casework/tracks/meta only. Agent code stays in server/ and route handlers.
    • core never imports a track. Tracks import core.
    • Every folder has an index.ts. Import from the folder, never a deep file.

    Why it stays modular

    • Track knowledge is in one folder, so a fifth track is one new folder.
    • The UI only reads events, so live, replay and recorded fixtures all use the same code path.
    • run/view.ts is shared by the web app and the ANSWERS writer. What judges read and what the demo shows can't drift apart.
    • Directions are token files plus two skinned components. Picking a direction later costs nothing.

    Performance and reliability

    Two kinds of speed matter. The UI has to feel instant in the demo. The agent has to finish every unseen case in the Reality Test window without anyone stepping in.

    ≤ 170 KBFirst-load JS on /inbox, gzip
    ≤ 1.2 sLargest contentful paint on the inbox
    ≤ 100 msFrom SSE event to trace step on screen
    60 fpsAnimations use only transform and opacity
    ≥ 90%Prompt cache hit rate on system + tools + policy
    0Unhandled errors that end a batch

    Frontend

    • Server Components by default. Next splits per route. Only interactive pieces (trace, controls, voice) are client components, so static panes ship no JS.
    • Load animation code lazily. Use LazyMotion with domAnimation and the m. components, which saves about two-thirds of motion's size. Mascot and chip animations are plain CSS keyframes.
    • One stream per run. useRunStream parses each event with zod, reduces with runView, and batches renders with startTransition. On reconnect it resumes from Last-Event-ID.
    • Memoise trace steps. They're keyed by seq and only re-render when their own event changes. Long traces are virtualised once they pass 200 steps.
    • Virtualise the inbox with @tanstack/react-virtual once there are more than 100 cases.
    • Fonts: next/font self-hosts variable latin subsets with display: swap. Each direction’s faces are CSS variables.
    • Icons are named imports from lucide, so only the icons used are bundled.
    • Query cache: cases stay fresh for 30 s. A human decision updates the case optimistically and rolls back on error.
    • Shared clock: one 30 s ticker drives every RelativeTime and SlaTimer, instead of one interval per row.

    Agent and API

    • Prompt caching. Order the prompt as system, then tool definitions, then track policy, then case sources, with cache breakpoints after policy and after sources. Every turn after the first reads from cache.
    • Two models. The fast model summarises and tags each source once. The decision model only sees the summaries plus the raw passages it cites.
    • Parallel tools. Let Claude make independent tool calls in one turn, and run them with Promise.all inside the guard.
    • Retry wrapper. Timeout per tool, 3 attempts with exponential backoff and jitter, and an idempotency key per call so a retried booking can't double-book. Every attempt emits an event.
    • Failures become events, not crashes. A tool error is returned to the model as a tool_result with is_error, so it can recover or escalate.
    • Hard limits: max 12 turns and a token budget per case. If either is hit, the run escalates with the context so far rather than failing silently.
    • Batch throughput: p-limit at REALITY_CONCURRENCY. On a 429 the batch backs off as a whole. Each case's ANSWERS folder is written when that case finishes, so a crash keeps finished work.
    • Replay without spend. Events are stored in SQLite, so the demo and UI work can replay runs without calling the model.

An operations agent for messy real-world cases (calls, emails, documents, CRM, tickets).

## Where things go
- Schemas: packages/core/src/schema (zod). Change these first, in their own commit.
- Agent loop, guard, retry, handover: packages/core/src/agent
- Track data, tools, policy, prompt: packages/tracks/src/<track>
- UI primitives: apps/web/src/ui/<Name>/  Domain UI: apps/web/src/domain
- Pages: apps/web/src/app/(app)/<route>/page.tsx stay thin; logic in src/features/<route>
- API: apps/web/src/app/api/**/route.ts; server-only code in apps/web/src/server
- Reality Test CLI: apps/cli (runs the agent without Next)
- Design reference: /design route and docs/design/casework-design-directions.html

## Rules
- Colours, radii, fonts and shadows come from CSS variables in src/tokens. No hex values in components.
- Never name a track in core, api, ui, domain or layout. Use pack.vocabulary.
- Every new event type goes into RunEvent, runView, mascotFor and answers/render.
- Tool errors become tool.failed events. Never throw out of the agent loop.
- Prohibited actions are enforced in agent/guard.ts, not only in prompts.
- Money is integer pence. Format with lib/format.money.
- Server Components by default; add "use client" only where there is interaction.
- Every UI component: all states in /design, keyboard reachable, honours reduced motion.
- Never hand-edit ANSWERS/. Re-run the CLI instead.
- Never commit .env or keys. .env.example lists every variable.

## Definition of done
typecheck, test and build pass · component is in /design · README updated if behaviour changed

    Picking up a task

    1. Read CLAUDE.md, then this piece's catalogue entry. Use its build brief as the prompt.
    2. Work only inside the folder your workstream owns. Contract changes are a separate commit.
    3. Build against fixtures and msw. Don't wait for the backend.
    4. Add the component to /design with every state from its entry.
    5. Run pnpm typecheck && pnpm test, then open it with the run skill.
    6. Before committing, run /code-review on the diff.

    Done means

    UI component
    • Uses tokens only. Looks right in all three directions.
    • Works with all four tracks' sample data, with no track words in the code.
    • Every state listed in its entry renders in /design.
    • Keyboard reachable, visible focus, a label for every control.
    • Status always has text as well as colour. Reduced motion gives the static pose.
    • No horizontal scroll at 400px wide.

    Done means

    Server module
    • Input and output validated with the shared zod schema.
    • Emits events for everything it does, including failures.
    • Tested against recorded fixtures, with no network in unit tests.
    • No secrets in code, logs or traces.
